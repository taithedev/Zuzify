# Zuzify Communications rollout

The XYZ portal now has authenticated support tickets, an inbox, email preferences, and server-only rank/news/reply event endpoints. No email is sent merely by deploying.

1. In the Zuzify Accounts Neon database, confirm the managed neon_auth."user" table has id, email and "emailVerified". Apply apps/xyz/db/communications.sql using the SQL editor. Use a restricted server-only database role with SELECT on these user columns and required access to the new schema, not browser credentials.
2. Set the XYZ Vercel server environment variables in apps/xyz/.env.example. Verify the actual session JWT issuer and audience against Neon Auth configuration. Do not reuse an OAuth client access token. Require working email verification in Neon Auth.
3. In an authorized email sending provider account, verify zuzify.xyz in Resend using its exact DNS records; do not replace existing MX records. Configure DKIM, SPF and DMARC. Create a restricted sending key. Set RESEND_API_KEY. A sender address is not a mailbox; arrange receiving/forwarding for support@zuzify.xyz and set ZUZIFY_SUPPORT_INBOX to an actual monitored address. News and notifications are outbound only.
4. Set CRON_SECRET to a random 32+ character secret. Have an authenticated scheduler invoke GET /api/dispatch using Authorization: Bearer <CRON_SECRET>. Start with a manual test account and test opt-out, rate limit, retry, and reply. The worker attempts ten messages per invocation, up to five times; monitor unsuccessful rows. Do not schedule until domain and preferences are verified. Provider acceptance is not guaranteed delivery.
5. Give each trusted app backend a distinct 32+ character key in ZUZIFY_APP_EVENT_KEYS (JSON map). Never place keys in desktop, game, web or mobile clients. Verify that the user explicitly linked their app account to the central Zuzify ID. On a committed rank change POST /api/events with Authorization: Bearer <app key> and JSON {kind:"rank",app:"ZuzuCord",userId:"central verified id",eventId:"unique persistent event id",rank:"Developer"}. The same event ID is deduplicated.
6. An authorized support operator uses the admin key and POST /api/events with {kind:"ticket_reply",ticketId:"uuid",eventId:"unique id",reply:"reply",close:false}. The latest reply appears in the account center. Staff ticket listing/queue is not a public API; authorized database operators can view the queue. Do not disclose ticket content in email.
7. An authorized operator can publish a single user's news event using the admin key and {kind:"news",userId:"central verified id",eventId:"unique id",title:"headline",message:"text"}. This creates an inbox notice; email is only attempted when the user has actively opted in. Before bulk campaigns, implement one-click unsubscribe, suppression/bounce handling and applicable mailing requirements. No bulk campaign is implemented.
8. Test in a preview environment before merging to production. Existing Discord pairing and OAuth flows are unchanged. Separate app integrations, production secrets, DNS, receiving mailbox and scheduled dispatcher are rollout tasks, not established by this commit.
